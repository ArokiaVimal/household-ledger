## Re-reading an already-imported file (added)
- Uploading the same statement (same bytes, same payment method) is no longer a dead end. The preview reports `previousImport`; the Import screen shows **"Read this file again?"** with the numbers and the preview stays hidden until you answer. **Yes** shows the normal preview (rows still in your ledger or review queue are skipped as duplicates; rows you rejected or removed come back for review). **No** clears the file. If nothing would be added the dialog says so and only offers Close. The server enforces it: committing without `reimport=1` is refused (`already_imported`), a confirmed repeat is stored as a new batch with `reimportOf` and a RE-IMPORTED audit entry, and the history list shows "Read again".
- Tests: service tests (previous import reported, refusal without consent, rejected rows come back once, nothing added when all present) and a real-Firestore test. A bug found while checking it in the browser: the dialog's own "closed" event was cancelling the import after Yes; fixed.
- Not checked in the live app (needs sign-in); checked in the browser with a faked server reply at desktop and phone width.

## Import → review → dashboard flow (added)
- After a successful import (at least one row staged) the Import screen sends you straight to `/review?imported=N&skipped=M`, which shows a one-line confirmation and, while the rows are still arriving from the server, a "Loading your N imported transactions…" state (it gives up after 8 seconds and shows the normal queue). The query string is removed once the queue has been cleared.
- **First time only:** when the review queue goes from having rows to empty and something has been approved, you are taken to `/?reviewed=1` (the dashboard shows an "All caught up" strip with Dismiss). The once-only flag is stored in this browser (`localStorage` key `pf:first-review-done`), so a different device or a cleared browser will do it once more. Clearing the queue again later just shows the empty queue.
- Verified in a browser (demo mode): approving all waiting rows redirected to the dashboard the first time and stayed on the review page the second time; the confirmation strip renders. **Not exercised end to end on the live site:** the Import → Review jump after a real upload.

## Undo, audit trail, rollback, backup, restore, deletion (added)
- **Audit trail:** every change to a transaction (edits, approvals, exclusions, splits) logs who, when and what changed (`AuditEvent.change` holds the before and after of the classification, split and status fields). Settlements, rules and categories were already logged. Screen: **Activity** (`/activity`, signed-in only).
- **Undo** (`audit.undo`): steps back one change at a time (only the newest change of a transaction), refuses when the transaction changed another way since (so it never overwrites), covers category edits, exclusions and import approvals (an approval goes back to waiting for review), never touches the original bank fields, and is itself logged (and undoable). Merchant memory learned from an approval is not unlearned.
- **Import rollback** (`batch.rollback`, Activity → Imports): removes the transactions the import created (approved or waiting; copies shared with a partner or linked friend are withdrawn), removes card bills it created, keeps the immutable source rows and the batch record (stamped rolled back), and lets the same file be imported again. Refuses while any of its transactions are in an unvoided settlement. Older batches are matched through the import tag on the row; new imports store `batchId`.
- **Backup / restore** (`src/lib/backup/backup.ts`, `/api/backup`, Settings → Your data): one JSON with every collection of the personal space, counts and a SHA-256 checksum. Verify checks format, version, every row against its schema, duplicate ids, counts and checksum, plus warnings for references outside the file. Restore needs a verified backup and the typed word RESTORE, replaces the space's data, keeps the original audit ids and times, and puts the previous data back if the restore fails part way. Partner and linked-friend shared spaces are not part of a personal backup.
- **Deletion:** Settings → Delete all my data (typed DELETE MY DATA) removes the whole personal space and the person's account links (and their copies); sign-in and the joint partner space are untouched.
- **Sync now** (Settings → Your data): refreshes data and compares the live version (Git commit) with the one the phone is running, with an Update now button.
- Not built: an in-session Undo snackbar right after an edit (Activity is the place), undoing rejections, and verifying a restore against live Firestore (tested with the in-memory repository).

An email or text that names no card is saved with `needsCard` set; the row shows "Pick a card", Verify opens the edit screen with "Paid with: Choose", and Save & verify stays off until a card is picked. Swipe-verify and "Verify N sure ones" skip these rows. Setting a payment method is allowed only while a row is unverified (server checks this). A stored placeholder account still exists internally for these rows.

## Wallet spends are paid with the wallet's voucher (2026-10-21)
A purchase or fee under a voucher wallet account (Amazon Pay) now gets `paidWithVoucherId` automatically: at import (statement, pasted text, Gmail, SMS), on verify (server and screen), and through the one-time repair action `records.fixWallets`. These never count again in spending; the Shopwise voucher purchase on the card is the outflow. Found by cross-checking the Amex statements: 32 unmarked Amazon Pay rows counted ₹11,291.25 twice in September.

## Transactions: vouchers as one line per brand and month (2026-10-21)
In the All and Verified lists, every purchase of a voucher brand in the month (three Amazon vouchers bought through Shopwise) is added into one "Amazon voucher" line. Expanding it shows "Bought" (the purchases, labelled Voucher, no category) and "Paid with it" (payments made with the voucher, with their own category and split, plus wallet top-ups and refunds). Payments never count again. Voucher-paid rows are kept in the list even though a payment group counts them as nothing (`recordsFor` in the store). Purchases with no brand chosen yet stay as plain rows. Code: `voucher-section.tsx` and the Transactions page.

## Card payment history and one payment, one entry (2026-10-21)
Cards tab: each card has a Payment history (newest first, 3 shown, the rest under "Show more", link to Transactions). `cardPayments` in `cardbills.ts` joins the card's own "payment received" line and your bank's debit into one payment (same amount, dates within 3 days; two lines on the same side merge only on the same day). Bill status and the Timeline use it, so a payment seen from both sides counts once (the Timeline would otherwise have shown it twice). Unverified payments are included and marked. A card-due message no longer adds a bill when a statement already made one for the same card, due date and amount. Vouchers: "Bought" and "Paid with it" show their totals.

## Nicknames everywhere (2026-10-21)
Every place that shows a person now goes through `nameOf` (nickname first): People pages and their Paid by / Paid to lists, recurring and transaction "Paid by" chips, group members, activity. Your partner's account name is theirs, so what you call them is stored on your own account (`users/{uid}.partnerNickname`, route `/api/partner-nickname`, applied in the app layout like profile photos). Set it under Settings > Friends & Family > edit your partner. Split sheet: people in one row of five (most used first); Quick splits are the first option of the How row.

## Logos and icons you can choose (2026-10-21)
A merchant now shows a logo or an icon, never both. Order: a logo you or AI chose (`merchantMemory.logo`, a file in `public/logos`, list in `LOGO_KEYS`), else a known brand logo or badge, else a chosen icon, else a fallback (the person page uses the category icon), else the first letter. AI may answer with a logo only from our own files and only for merchants. Settings > Icons & logos: "Suggest for new items" and "Redo everything"; each suggestion with a logo has a Logo / Icon switch; saving a logo clears the icon and the other way round (`icons.apply`). Not yet checked on screen because the Firestore free daily read quota ran out during testing (see chat).

## Self-healing for a frozen app (2026-10-21)
`Pwa` (src/components/pwa.tsx, rules in src/lib/self-heal.ts): a tap on a link that has not reached its page after 8 s loads that page the plain way; coming back to the front after 5+ minutes checks `/api/version` and reloads when a newer build is live; after an hour away the screen reloads; nothing reloads while a dialog is open. Cause of the reported freezes is not proven (no way to reproduce on the phone); these make the app recover by itself.

## Paid with on every transaction screen (2026-10-21)
Add and Edit now always show "Paid with" (and "Via" for sub methods). It can be changed on manual entries and on rows from an email, a text message or pasted text (their card was worked out or guessed; `accountIsEditable` in `domain/accounts.ts`, enforced by the repository guard). A row read from a statement file keeps the statement's card: the row is shown locked with "Set by the statement it came from". Moving a payment out of a voucher wallet removes its paid-with-voucher mark; moving into one adds it. The person page now opens your own record, not the shared copy. This also fixes "Pick a card" on email/text rows, which the old guard would have refused on save.

## ICICI statements, long statements with AI, and clearer feedback (2026-10-21)
`parseIciciBank` (src/domain/import/pdf/icici-bank.ts) reads the ICICI Bank account "Statement of Transactions" PDF from positions and checks every row against the statement's own running balance, the opening/closing arithmetic and the row numbers. The AI read now splits a long statement into pieces of about 6,000 characters (a few overlapping lines, the heading repeated), reads them in parallel and merges the answers, so one answer never has to hold every row; a piece that fails is reported, not fatal. Import shows a blocking progress pop-up (with a timer) while reading, asking AI or saving, and every error appears as a pop-up.
